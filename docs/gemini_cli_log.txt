   And yes, **start on your desktop**.

   ### 🔹 Why Desktop First
   - Audio journals = large binary files + transcription + embedding generation. Desktop has the storage headroom, sustained CPU/GPU, and won’t
   throttle like a laptop on battery or under gaming load.
   - You’ll run heavier local models and background sync services here. Laptop stays light for orchestration + gaming later.
   - Dockerized setup means you’ll replicate the exact same stack to laptop/Surface later with zero rewrite.

   ### 🔹 v1 Blueprint (Desktop)
   | Layer | Tech | Purpose |
   |-------|------|---------|
   | **File Storage** | Local `~/data/audio/` + Rclone/Syncthing later | Raw `.wav`/`.mp3` files |
   | **Metadata DB** | SQLite + `sqlite-vec` or PostgreSQL + `pgvector` | Journal titles, timestamps, tags, transcript pointers |
   | **Vector Store** | `sqlite-vec` (same DB) or local Qdrant | Semantic search over transcripts |
   | **UI** | Streamlit or FastAPI + HTMX | Upload, play, search, view transcripts |
   | **Pipeline** | Whisper.cpp (quantized) + FFmpeg | Transcribe → chunk → embed → store |
   | **Runtime** | `docker-compose.yml` | Isolated, reproducible, easy to move later |

   ### 🔹 How to Iterate
   1. **Week 1**: Get audio upload → transcribe → store metadata/embeddings → basic search UI working locally.
   2. **Week 2**: Add tagging, cross-reference, and export. Wrap in Docker.
   3. **Week 3**: Introduce first agent (e.g., auto-summarizer or alarm trigger) that reads from this DB.
   4. **Week 4**: Add router + NATS, replicate stack to laptop, test cross-device sync.

   ### 🔹 Key Rule for This Phase
   Keep the DB schema **agent-agnostic**. Store raw audio path, transcript chunks, embeddings, and user-defined tags. Agents will query this layer
   later; don’t bake agent logic into the data model yet.
